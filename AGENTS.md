# Campaign Hub

## Purpose

Campaign CRM integration, campaign delivery reporting, and creator operations.

## Ownership

- `campaign_manager/` owns the API and scheduled backend work.
- `frontend/` owns the web interface.
- `tests/backend/` owns backend verification.

## Local Contracts

- Railway startup requires a non-whitespace `SECRET_KEY`; preserve any configured nonblank key byte-for-byte so Flask sessions use the same signing key across processes and restarts. Local development may generate an ephemeral key when none is configured.
- Public `/health` reports `db_target` using the same SQLAlchemy URL grammar as database initialization, exposing only the scheme and host. Credentials, port, path and query stay private; absent URLs return an empty target; unparseable URLs or URLs containing multiple raw `@` separators return `set` because the parsed host may contain a password fragment. This conservative diagnostic fallback also applies when the extra `@` is in a query; it never changes the database connection.
- `/health` reports `schema_repair: "ok"` after the required PostgreSQL `campaigns.completion_status` repair succeeds. A failed repair returns `ok: false` with HTTP 503; it does not expose raw database errors, and the campaign scheduler must not start until repair succeeds. Health probes retry repair with bounded exponential backoff and a per-process nonblocking guard, so transient boot-lock contention can recover without a process restart or probe stampede. During expired schema verification, concurrent probes fail closed until reconciliation finishes. When readiness recovers, the health path reconciles scheduler startup under the existing process-wide file lock. Successful state is checked read-only every 30 seconds; detected column/default/NULL drift triggers the migration again. The narrow versioned migration backfills NULL values to `none` and restores the database default so active-campaign exclusions retain existing rows.

- CRM `Content Niche Targets` supplies the declared campaign niches consumed by ShipStream's D1 playlist flow.
- The CRM Client discovery job reads one bounded Notion query page (50 rows) per minute tick, resumes the query cursor across ticks, and wraps after the last page. Malformed rows are skipped with bounded, content-free diagnostics so later rows on that page proceed; a database connection or pool failure stops the batch and restores the pre-query cursor for retry on the next tick. It uses a create-only insert protected by the existing unique constraints, so replay and concurrent campaign or creator writes preserve existing rows. Slug matches never change an existing campaign's CRM identity, categories, or captions. Existing linked campaign refresh remains owned by the bounded active-campaign 15-minute lane reading exact stored page IDs.
- Campaign reads request a background refresh at most every 15 minutes, independent of the scraping scheduler. The refresh reads exact stored Notion page links for existing active campaigns, updates only `content_types` and `internal_captions`, and neither creates campaigns nor sends notifications.
- An unreadable or missing CRM property preserves stored categories; an explicitly empty multi-select clears them.
- CRM `Internal Captions` holds a campaign's text-on-screen lines, typed by staff or submitted on an intake form. The same refresh keeps each active campaign's copy current, verbatim, under the same preserve-or-clear rule; a value too long to read whole counts as unreadable, never as a shorter list. Saving a whole campaign never changes its captions once it exists.
- `GET /api/campaigns/captions` lists every active campaign whose CRM captions have been read, with its sound, for the posting control plane. Finished campaigns and campaigns never read are left out, and the campaign list itself carries no caption text.
- `PUT /api/campaign/<slug>/internal-captions` saves one campaign's captions from the posting control plane, CRM page first, stored here only once the CRM took it. The caller sends `expected`, the value it last saw; a different stored value answers 409 with the current one. When `HUB_WRITE_KEY` is set the `X-Hub-Write-Key` header must match.
- `POST /api/migrate/campaign-full` is a privileged migration writer and requires the existing `HUB_WRITE_KEY` via `X-Hub-Write-Key`; it returns 503 when the key is not configured and 401 for missing or incorrect credentials. `?overwrite=1` does not bypass authentication. Authorized migrations retain the existing create/overwrite behavior and sound URL uniqueness checks.
- HTTP(S) `official_sound` assignments use normalized scheme, host, default port, path, query, and no fragment as URL identity. API and Notion campaign creation plus `/api/migrate/campaign-full` imports check duplicates under the shared PostgreSQL advisory lock; migration overwrite uses the stored link as its expected revision. Legacy `POST /api/campaign/<slug>/edit` requires `expected_official_sound` for URL changes and rechecks it under that lock. `PUT /api/campaign/<slug>/sound-link` uses the same CAS and duplicate guard, updating `official_sound` and `sound_id` atomically; it derives IDs from TikTok music URLs and clears stale IDs for other links. Duplicate assignments return 409. URL assignments through create, edit, or sound-link return 503 when only file-backed storage is available because scan-then-write cannot enforce global uniqueness across workers. Non-URL sound-ID edits retain their existing behavior.
- The campaign editor displays the stored official sound URL ahead of its numeric ID. An ordinary save omits unchanged HTTP(S) sound fields, preserving the stored URL and resolved or absent ID. Intentional URL edits send the revision displayed when editing opened; numeric edits and explicit clearing retain their existing payloads.
- Campaign API and Notion webhook creation accept only `save_campaign` results `None` or `updated` as success. Duplicate assignments and concurrent revision conflicts return 409 before creator writes or success reporting; unexpected save results fail closed. Notion sync skips known duplicate/conflict outcomes and reports unexpected save failures without listing those campaigns as created.
- Dated campaign rounds sharing an exact primary or additional sound own posts from their start date up to, but excluding, the next round start for that *video's sound*; completed later rounds still close that sound's earlier window, and same-day ties resolve by creation time then slug. An identified secondary sound stays eligible after a different primary sound advances. A matched video without a trustworthy campaign-owned sound ID uses the earliest overlapping successor as a conservative cutoff; excluded ambiguous posts are logged under a stable hash of the URL without query or fragment, or by row ID if no URL exists, for reconciliation. Never silently upload those posts to Cobrand or log raw URLs with possible query tokens. Posts with missing or invalid dates and campaigns with invalid nonempty start dates cannot prove membership. Internal auto-attach chooses the latest active eligible round. Scheduled and manual scrapes filter candidates and stored aggregates by the round window; campaign detail, links, list, creator aggregates, client report, Chartmetric post events, Cobrand untracked queue/bulk tracking, and sideload upload batch use that same window. Cobrand outcome joins require a nonempty URL matching an eligible post. Existing matched-video rows remain stored. Campaigns without a start date retain legacy behavior. File-mode campaigns lack a reliable all-campaign roster, so cross-worker upper-bound isolation is only established for DB-backed paths. Hub does not persist daily campaign-stat snapshots; Chartmetric history is fetched from its service, and any new local time-series feature needs an explicit storage and reader contract.

- Sound Assignments sends the optional server-only CONTENT_LAB_HUB_API_KEY as X-API-Key to its configured Content Lab proxy. Browser headers never supply this credential. Configured-key requests do not follow redirects, and transport errors do not expose the key. Without the key, existing upstream behavior remains unchanged.

- Local Hub queue export and helper defaults use the canonical https://campaignhub.risingtidesviral.com origin. Queue export accepts only an HTTP(S) origin or that origin ending in /api from CAMPAIGN_HUB_API_URL; reject credentials, query, fragment, other paths, invalid ports and limits outside 1-5000 before network or output creation. Report HTTP, transport or JSON failure without copying response bodies or token-bearing URLs, and create no successful export receipt on failure. The standalone POSIX main-thread exporter caps queue response bytes at 32 MiB and the whole HTTP exchange at 45 seconds; it rejects incomplete declared bodies before writing output or a receipt. Other-thread/non-POSIX callers retain a socket timeout and between-read clock but do not have a strict whole-exchange bound, and a pre-existing ITIMER_REAL alarm can be delayed while this CLI deadline is active. The internal-groups CLI retains its separate CAMPAIGN_HUB_API override.

- Local scraper delegation accepts a node launch only when `/api/run-now` returns `ok: true`, `action: "scrape"`, and `started: true`, or `started: false` with the exact `scrape already running` note. An explicit node refusal is failure; malformed or transport responses have an unknown outcome and require reconciliation with the original local run before any retry. Return normalized node fields and fixed diagnostics without launch details or token-bearing URLs. A launch acknowledgment is not proof that scraping completed.
- Campaign and internal cron scrape bodies each claim their own nonblocking PostgreSQL session advisory lock across APScheduler, manual and Hub on-demand entrypoints. Duplicate same-type runs skip before scraping. Distinct job types additionally share a scrape-capacity advisory lease: the later job keeps its queued receipt and waits up to 60 minutes with bounded backoff, then fails explicitly if capacity remains busy. Both leases are checked before persisted scrape results; lost sessions abort remaining work. SQLite/file-mode development has same-host OS file locks only. The separate Mac local-agent runner has its own launchd guard, not the Hub database lock, so cross-host capacity and end-to-end exclusion remain unverified.
- `POST /api/cron/toggle` is retired and always returns HTTP 410 without changing scheduler state. A request could reach a nonowner Gunicorn worker and falsely report a fleet-wide change; operators use `SCHEDULER_ENABLED` with a controlled service restart, then verify the scheduler owner. Keep this endpoint side-effect free.
- `GET /api/cron/diag` is retired and always returns HTTP 410 with a fixed response. Neither the default route nor query parameters run yt-dlp, fetch proxy/TikTok content, or reveal scraper configuration; use controlled internal diagnostics and durable cron receipts instead.
- `CAMPAIGN_REFRESH_SCHEDULER_ENABLED` defaults to true and gates only APScheduler's automatic `campaign_refresh` job when the overall `SCHEDULER_ENABLED` switch is on. Setting it to false requires a process restart; startup loads the SQLAlchemy jobstore paused, removes any persisted older `campaign_refresh` job, then resumes internal scraping, Notion and other jobs. A failed removal leaves the scheduler stopped for readiness retry. Manual and on-demand campaign refresh retain their normal leases and receipts. Use false on Railway only after the Mac has the approved Apify credential and its own delivery path is verified; rollback by restoring true and restarting Railway, then verify `campaign_refresh` is registered while the other jobs remain scheduled. This switch alone does not establish cross-host exclusion or completed Mac delivery.
- Scheduled TikTok creator discovery uses `src/scrapers/master_tracker.py` through `campaign_manager/services/scheduler.py`. A failed yt-dlp exit, empty or unusable output, timeout, or unexpected fetch exception is a typed source error, never a successful zero-video scrape. The scheduler retries source errors at most once with backoff, preserves previously confirmed cache rows for matching, and records each creator's sanitized status, reason code, and available cached-row count in the durable cron summary. Complete TikTok source failure for any requested creator roster, or more than 70% source failures across a fleet of at least six, marks the run degraded independently of the existing empty and native-crash thresholds. Raw yt-dlp stderr, command arguments and exception text stay out of receipts and logs; native signal failures retain their separate classification. Valid fetched rows filtered out by date remain an `empty` outcome.
- Campaign refresh marks a run degraded when every requested Instagram creator scrape fails or returns no usable outcome, even if campaign bookkeeping completes; its Slack notice reports requested-creator Instagram outcome counts, including missing/unknown outcomes. It describes all reported errors as failures and missing or conflicting evidence as unavailable outcomes. Outcome keys are normalized against the requested names; unrequested results cannot mask failure, and conflicting aliases count as missing regardless of map order. Partial Instagram failure does not change the existing TikTok-only empty/crash anomaly thresholds. A completed cron status records execution completion, while `summary.degraded` carries scrape quality.
- Manual `POST /api/cron/trigger` records a durable queued cron request before dispatch and returns `log_id`. For Hub jobs, HTTP 202 `accepted` means queued, not executed; poll `GET /api/cron/logs/<id>` for queued, running, skipped, completed or failed. For configured local campaign delegation, the receipt first commits `dispatching` before the node POST, and becomes `delegated` only on the normalized node launch acknowledgment, `skipped` if already running, `failed` on explicit refusal, or `unknown` on ambiguous response; these are dispatch outcomes, never proof of scrape completion. Do not resend unknown outcomes before original-run reconciliation. A duplicate Hub request becomes skipped, with an active ID when unambiguous. The janitor fails orphaned queued requests without executing them and marks orphaned `dispatching` as `unknown` requiring original-attempt reconciliation. PostgreSQL Hub receipts bind to the exact job-lock session before waiting for shared capacity; the internal identity stays out of cron log API responses. The janitor locks stale receipt rows before deciding their owner, preserving only queued/running receipts matching the current session, so a newer same-type run cannot keep an older orphan alive or race with a concurrent bind. A pre-deployment unbound receipt is conservatively preserved for at most 24 hours while a lock has no matching bound receipt; after that its receipt fails even if a lock remains. This compatibility cap does not prove the old worker stopped; reconcile its original run before retrying effects. Scoped local scrapes are refused before node dispatch because the current node ignores slugs and runs all active campaigns. The local active-campaign child treats only an exact same-type `already_running` skip as no-op exit code 76; other skipped reasons remain failures with `skipped` and `scrape_outcome` in its report, and omits queue export. The canonical hourly wrapper maps only code 76 to neutral `SCRAPER_STATUS.json` stage `skipped` and exits 0; the reserved code 77 marks an export failure after a healthy completed core scrape as `export-exit`; degraded core scrapes remain scrape failures even if export also fails; other nonzero codes remain scrape failures. The child report keeps core `scrape_outcome` separate from `failure_stage: export`, so neither a no-op nor an export failure erases the core outcome.

- Backend song-link scraping uses `src/scrapers/yt_dlp_runner.py` for yt-dlp command and environment policy. Redact configured `--proxy` and `--cookies` values from copied stderr and runner exceptions before truncation, logging or propagation.

- Local yt-scraper command diagnostics redact every `--proxy` value, including credentials and query parameters; the actual yt-dlp arguments remain byte-for-byte unchanged. Copied yt-dlp stderr also redacts complete configured proxy values before first-line truncation, preserving other error context. Drain stdout and stderr concurrently within the per-account deadline while retaining at most 8 MiB of stdout and 16 KiB of raw stderr per account. Excess stdout fails with zero accepted rows; excess diagnostics carry a truncation marker after configured-proxy redaction, including proxy fragments split at the retained boundary. Incomplete output must not produce a completed scrape. Unix subprocesses own a private process group, terminated on timeout, wait/read failure, incomplete collection, or oversized stdout; Windows currently terminates only the direct child and has no verified descendant-cleanup guarantee.

- The local yt-scraper GUI binds only loopback IP addresses or localhost. Validate Host, Origin and browser fetch-site headers against the actual listening address/port before reading bodies or dispatching any action; trusted local CLI calls may omit Origin. Keep the GUI same-origin and do not add a remote-access mode. The existing listener uses Hyper HTTP/1 with at most 16 admitted connections and owned connection-task records, one 30-second deadline from accept through headers and complete decoded body, a 32 MiB decoded body cap, and a 5-second response-write bound. Refused, oversized, malformed or incomplete ingress closes the owned connection without draining the remaining body and invokes no business action. Admission remains held until both connection and complete synchronous handler/logging closure finish; responses retain synchronous write-completion semantics with cancellation acknowledgment; accepted Pi/proxy action deadlines and run-history/job policy remain separate. GUI Hub proxy requests use ureq's 30-second overall timeout for connection, response headers and body, including a progressing body. DNS resolution cannot be interrupted by this timeout. Transport and incomplete-body failures return HTTP 502 rather than a successful empty object.

- Pi CLI chat reuses the scraper's concurrent bounded pipe readers and process-group cleanup. Its existing 15-600 second timeout covers child exit and complete stdout/stderr collection from one monotonic spawn deadline. Retain at most 8 MiB stdout and 16 KiB stderr; refuse incomplete or oversized replies and keep failure diagnostics bounded. Record chat history only after a complete successful reply. Timeout, wait/read failure, nonzero exit and refused output cancel readers and terminate the owned Unix process group; Windows remains direct-child-only. Preserve the Pi command, prompt, inherited stdin and API response shape.
