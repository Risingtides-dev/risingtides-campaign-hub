John approved running the one-time `POST /api/trackers/sync-status` backfill so campaigns already marked finished show Complete on their TidesTracker pages (the tracker began accepting status on 2026-11-07; the per-save push from `edit_campaign` was proven live that day on Bella Kay Wonder Wander Round 4). The production call at 12:13Z on 2026-11-09 answered `{"ok":true,"pushed":0,"failed":329,"total":329}` in 0.34 s, no tracker row changed, and Railway held no "tracker status" log line. Cause: the route fans `set_tracker_status` out on a ThreadPoolExecutor, `set_tracker_status` reads its config through `flask.current_app`, pool threads carry no application context, so every call raised RuntimeError before any request left, and the route's bare `except Exception: return False` hid it. The per-save path is unaffected because it runs in the request thread.

Repair: capture the real app in the request thread, enter `app.app_context()` inside each worker call, log a crashed push with the tracker id instead of swallowing it, and log one summary line per run. An independent read-only review of the first diff found nothing blocking and pointed out that `campaigns.tracker_campaign_id` is not unique, so two campaigns naming one tracker with different statuses would race across threads now that the route sends anything at all. The route therefore pushes each tracker once, as `complete` only when every campaign naming it is finished, and returns the number of such disagreements as `conflicts`. The per-save path stays last-writer-wins. AGENTS.md records the contract, including that campaigns tied to a tracker only through the `tracker_campaign_links` overlay are covered by neither path.

Verification: three new tests in tests/backend/test_tracker_status_push.py drive the route through the test client without stubbing `_config`; before the repair the first failed with pushed 0 / failed 2, the same shape as production. Full suite `python -m pytest -q -p no:cacheprovider` on the Hub venv (Python 3.10.19) passes with only the PostgreSQL-only and healthy-pip cases skipped. `git diff --check` clean.

Release limitations: at the time of writing this candidate is not merged, not deployed, and the backfill has not been re-run; no production data changed beyond the failed no-op call. Whether production holds any shared tracker was not measured before deploy because no list endpoint exposes `tracker_campaign_id`; the `conflicts` count in the first live response answers it. The route is unauthenticated and writes the same value on every run, so re-running is safe, but each call now holds one of four sync gunicorn workers for the length of the walk; gunicorn allows 120 s, and a tracker that hangs for the full 10 s client timeout on every call would exceed that and end the request without a summary. Roll back by reverting this commit; the per-save push does not depend on it.
